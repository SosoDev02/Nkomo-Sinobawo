## Reflection 
- **Situation:** A feature such as “checkout” was too big to assign to one person or finish in one day. We needed a way to break it down so everyone knew what to do and how it served the user.
- **Task:** I was responsible for building the shopping cart, implement cart persistence, checkout form (but it was shared among other members as well), and email and order confirmation.
- **Action:** We wrote stories in the form *As a user, I want a checkout feature to weigh my options , so that it will be convinient for me and we split each into subtasks with the team. My tasks leaned towards testing, integration and deployment, for example unit tests for the product API, integrating authentication with the cart, and deploying the sprint.
- **Results:** Each day we had a task that we had to complete as that day's sprint. I learned having sprints helps us with breaking down the work and focus on one task a day

## Product Backlog
### Evidence
After the project restructured, we rewrote the remaining work as day-by-day items, each with a user story: analytics and dashboard UI, reporting, expansion of the catalogue, end-to-end, regression and acceptance testing, documentation, launch preparation, monitoring, go-live, post-launch review and final handover.

## Reflection
- **Situation:** Our first backlog was planned phase by phase, and it assumed the whole team would be available for the whole project. When the team changed and the work moved faster than planned, it no longer matched reality.
- **Task:** Restructuring the product backlog breaking down each phase into subtasks for all the members
- **Action:** We wrote a revised backlog in which each item has a user story and five named subtasks.
- **Results** The backlog was more easier and specific on the tasks that the our first backlog. I learned that a product backlog serves as a dynamic and evolving list of features, user stories, and other tasks that the team works on.
